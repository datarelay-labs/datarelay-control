## Chosen top three gaps at comparison time (current disposition; preserve safety)

### P0-UI-REA-01 — Contextual per-Route failed-attempt drilldown (**FIRST runnable**)

Design: Extend existing read-only expert and narrow-screen Route Flow rows with **one explicit `Failed attempts` link when a Route is enabled and the existing authoritative numeric error evidence reports a positive error rate**. Preserve generic `Delivery logs`. Carry exact valid Stream, Route and optional Destination IDs via existing `logsExplorerPath({ ..., status: 'failed' })`, already understood by Logs Explorer and backend. Never claim the failure occurred *now* if the snapshot is stale, and never show a path-specific failure shortcut for disabled or unknown/error-rate=0 Routes. Do not copy competitor markup or add a preview/delivery API. **Acceptance:** RED→GREEN desktop/mobile tests on positive/zero/unknown/disabled/stale and invalid Destination ID; downstream Logs `FAILED` filter test passes; all existing links remain unchanged; source tests, ESLint, Vite build and exact HEAD CI. **Evidence level:** Source/native, NOT Browser FUE.

### P0-UI-REA-02 — One-click failed-filter empty-state recovery (**SOURCE IMPLEMENTED; CI/Browser GATES OPEN**)

Existing Logs Explorer already has a status-filter chip that can be removed without clearing Route, Stream and Destination identity. **Do not duplicate that capability.** The genuine source gap was specifically the **zero-result panel**: its primary choices were *Clear all filters* or *Open full logs*, both losing exact Route context just because the current `FAILED` subset was empty.

Implementation: On desktop **and** compact mobile empty-list states, when a saved positive Route ID is URL-scoped with `status=failed` and the API is reachable, show **Show all statuses for this Route**. This removes **only** the `status` URL parameter using the existing routing/state callback, preserving Route, Stream and optional Destination, as well as normal loaded-log filters and the original full-clear alternative. Never display this recovery if the API itself is unavailable or if Route ID/status evidence is missing. No extra API endpoint or server write.

Acceptance: a RED→GREEN actual page test drives `FAILED` API scope, clicks the recovery, then checks that the subsequent request drops only status while retaining the same numeric route/stream/destination identities. A compact mobile test separately verifies correct callback versus clear-all and no false-positive action on API error. Actual authenticated Browser and cross-page return still require approval.

### P1-UI-REA-03 — Path-selectable preview readiness / residual gap audit (**AFTER safety review**)

Design: Evaluate existing selected Route no-send processing preview against Splunk/Datadog path-specific simulation. Show only returned Mapping/Enrichment output and label Policy/Protection/receiver delivery **Not verified**; do not infer results from a pipeline canvas. Need a new independently authorized, non-denied source boundary before implementation. Acceptance: route change clears stale results, no actual send/writes, partial API failure explains missing evidence and retry, appropriate RBAC/mobile. **Block** if it would repeat an earlier platform-denied Wizard/Preview operation.

### P0-UI-REA-04 — Return from a scoped Route investigation to the next action (2026-10-10 KST)

**Documented precedent (not vendor source recovery):** The [Elastic Kibana Dashboard Drilldowns](https://www.elastic.co/docs/explore-analyze/dashboards/drilldowns) documentation describes preserving exploration context while navigating between an investigation and a detail surface. The preceding licensed Node-RED static REA pilot is **not** evidence of this Kibana behavior; no Kibana bundle, proprietary asset or authenticated session was analyzed.

**Verified Control source gap before this change:** Data Flows sends the operator to `/logs?route_id=…&stream_id=…&destination_id=…&status=failed`, and the page supports widening the failed-only filter while retaining exact identity. But when no matching logs exist, its existing actions offered a generic clear/widen workflow only; it lacked an explicit same-Route configuration follow-through independent of returned log rows. It is not sufficient to infer missing/healthy Route delivery or a receiver acknowledgment from that empty log panel.

**Bounded implementation:** A dedicated `LogsRouteReturnActions` is rendered in the existing Logs Explorer scoped-filter panel only for a positive safe-integer URL Route ID. It retains **Back to Data Flows** for all permitted read-only investigation users, and adds **Review Route #ID configuration** using the existing Route Edit URL only when the effective signed-in session has `workspace_mutations: true`; Viewer/read-only access gets a factual capability explanation instead of a mutating affordance. The return action remains available with zero loaded log results and does not resend events or create a new navigation/persistence/API workflow. Bad URL identities show no fabricated Route settings link.

**Evidence and limits:** RED missing-component test, GREEN pure role/ID/link tests and actual `LogsExplorerPage` empty failed-filter integration; adjacent Logs, Route Flow, narrow-screen and nav regression tests. Source tests and build/CI are distinct from actual browser acceptance; no current-head authenticated Browser BFS, 320/375/1440 visual review, or two-user Full User E2E is asserted. Previously denied Destination-create-return, parent Route view, sidebar, preview, Help and protected #410 Browser/DB workflows remain untouched.
